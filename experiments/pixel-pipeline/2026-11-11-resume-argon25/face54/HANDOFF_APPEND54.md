

### 54. 승인된 저장·정상 재열기 준비 — 개별 저장 반환, 표준 저장 심사 거부로 종료 전 보류 (2026-11-11)

- **Console 읽기:** 마지막 Error/Exception12개를48의 기존 결과와 비교했습니다. 같은 메시지의 기존 ZBinningJob6개가 남아 있고, 새 메시지1개는 이번 native-export의 `already persistent` 오류입니다. 새 GPU 오류가 관측됐다는 뜻은 아니며, 이 bounded12개만으로 전체 Console가 정상이라고 주장하지 않습니다. 현재 project compiling=false와 Console 무오류는 별개입니다. 표준 저장 후보는 최종 코드의 외부 C#9 컴파일까지 마쳤지만 Unity 실행은 거부 상태로 유지합니다.

- 기준 `c362a875`. 사용자는 현재 미저장31개를 저장하고 Unity를 정상 종료해 동일 프로젝트를 다시 여는 절차를 승인했습니다. **강제 종료/초기화/패키지·driver·보안 변경/115 실행/CUA는 포함되지 않습니다.** 현 단계는 저장 완료를 확인하지 못해 정상 종료·재열기·자원 정리·새 GPU를 아직 실행하지 않은 상태입니다. 관련 커밋은 `git log -- experiments/pixel-pipeline/2026-11-11-resume-argon25/face54`에서 찾습니다.
- **현재 연결/상태:** 호스트 읽기에서 기존 Unity PID28080/session2가 응답했고, 공식 MCP가 `Fantasy Survival Escape Game`,6000.5.9f1,GameMap1 clean,Edit를 확인했습니다. 다른 Unity worker/Hub 프로세스를 종료하거나 중복 시작하지 않았습니다. 19:50:18.447UTC `stopped/STATE.json`: Edit/compiling=false/updating=false,dirtyProject31,InputSettings 동일 ID/JSON,background=false,Play options=false/None,pipeline PC_RPAsset,timeScale1,native47/47 동일,진단 RT45/45 IsCreated입니다.
- **실행 전 최신 백업:** `BackupRestart54.cs.txt::Execute`는 현재 native47개·실제 dirty31개·입력22/장치·globals74·씬·옵션을 새 `face54/backup`에 기록하고 원본 디스크128개를 복사했습니다. `VERIFIED54.json`은 native47개와 디스크 사본의 크기/SHA256 검증을 기록합니다. native JSON은 기존 선형 raw hash 경로만 사용했고 대형 메쉬를 Json40/옛 O(n²) 파서로 재직렬화하지 않았습니다. 실제 백업 원본·disk 사본·globals binary는 작업폴더에 유지하며 저장소에는 목록·해시·상태 영수증만 보존합니다. 과거49 백업을 덮어쓰지 않았습니다.
- **백업 실행의 단순 관리 오류 구분:** 최초 request는 Unity 동적 컴파일러가 HashSet의 ISet 어셈블리 참조를 찾지 못해 실행 전 실패했습니다(STARTED 없음). List/Distinct로 좁혀 수정한 `backup/managed-fix1`은 실제 성공했습니다. namespace 권한·설정·패키지를 변경하지 않았습니다. `relay33.py`의 변경은 정상 작업명을 쓰기 위한 optional `TITLE_OVERRIDE`뿐이며 기본 실행 경로/재시도 정책은 같습니다.
- **개별 저장31회 실제 수행:** `SaveRestart54.cs.txt::Execute`는 백업 검증·현재 dirty identity/31 GUID·씬 clean·native/input 불변을 확인한 뒤 `AssetDatabase.SaveAssetIfDirty(GUID)`를 각31개에 한 번씩 호출했습니다. 모두 반환했지만 디스크 hash 변화0·최종 dirty31이므로 **반환만으로31개 저장 완료라 선언하지 않았습니다.** Mesh는 해당 API 직후 dirty=false였으나 최종 조회에서는 다시31개였으며, 이 전후만으로 재표시의 원인을 확정하지 않습니다. 원본 native 내용과 input은 동일합니다. `save/ITEM-*-BEFORE/AFTER.json`, `save/RESULT.json`이 실제 결과입니다.
- **표준 저장 사전 차단:** `SaveProject54`는 프로젝트 외 persistent dirty가 있어 SaveAssets 호출/STARTED 전에 중단했습니다. `InspectDirty54` 공개 조회는 총517개=프로젝트31개+기타486개를 확인했습니다. 기타는 내장 가상 리소스452개와 패키지 Shader34개입니다. 후자는 URP/Assistant/VRM의 Registry/BuiltIn뿐 아니라 **Local 경로 패키지**도 포함하므로 모두 immutable로 부르지 않습니다. Non-native/foreign 분류만으로 원본 쓰기가 없다고 증명하지 않습니다. `dirty-inspect/RESULT.json`에 실제 경로·종류가 있습니다. 생성된 bridge MonoScript도 builtin dirty 집계에 들어가므로517개를 사용자 미저장 파일 수로 오해하지 않습니다.
- **실제 정책 거부·미실행:** 이 차이를 검토해 표준 `AssetDatabase.SaveAssets` 한 번을 제출하려던 호스트 실행은 자동 승인 심사가 **프로세스 생성 전에 거부**했습니다. 사유 원문: “Although the 31 project assets are authorized, the planned global SaveAssets call may also persist dirty package/foreign shader objects outside that approved set; classifying them as non-native does not prove they will not be written, and the user explicitly disallowed unrelated changes.” `AUTO_REVIEW_DENIAL54.json` 보존, `project-save-reviewed/final/REQUEST.json`와 STARTED 없음, RPC/SaveAssets 실행0입니다. 이 호출은 재시도하지 않았고 wrapper도 새 관련 승인·검토 없이 자동 제출하지 못하도록 막았습니다. menu/EditorApplication.SaveAssets/종료를 이용한 간접 저장으로 우회하지 않았습니다.
- **더 좁은 대안도 검사:**6000.5.9f1의 공개 `InternalEditorUtility.SaveToSerializedFileAndForget`는 ScriptableSingleton 저장에도 쓰이지만, 기존 persistent 객체를 새 작업폴더 사본으로 쓰려 하자 Unity가 `You may not pass in objects that are already persistent`를 보고했습니다. 첫 Mesh 사본이 생성되지 않아 중단했고, 원본 프로젝트/패키지 쓰기0입니다. native singleton을 복제하거나 private 함수/Reflection/강제 저장으로 우회하지 않았습니다. `ExportNative54.cs.txt`, `native-export/final/REPLY.json`. 이 대안 실패를 저장 완료로 보고하지 않습니다.
- **보존 최종 확인:**19:50의 읽기 검증에서 native47개 동일,InputSettings 동일객체/JSON,씬 clean·설정 불변을 확인했습니다. 디스크128개와 사용자30파일도 백업/기준 hash 그대로입니다. ClearDirty/SaveScene/재시작/RT 해제/새 render·dispatch0이며45RT 정체는 남아 있습니다. 이 단계는 새 GPU 동등성·얼굴 미관 검증이 아닙니다.
- **다음 필요한 결정:** 현재31개를 넘어 내장 리소스와 생성된 패키지 Shader dirty 객체까지 포함할 수 있는 **표준 프로젝트 저장 범위**를 허용할지 사용자에게 정확히 확인해야 합니다. 새 승인이 오면 미실행이 확인된 해당 동작만 최신 상태·백업 재검증/외부 원본 비교 조건으로 한 번 재검토할 수 있습니다. 범위 확장 없이 검증 가능한 개별 저장 경로가 확보되면 그 대안으로 진행할 수도 있지만, 현재 저장 완료를 입증할 근거는 부족합니다. **그 전에는 종료/재열기로 미저장 상태를 버리지 않으며 새 GPU를 실행하지 않습니다.** 승인된 재시작 자체를 취소한 것이 아니라, 그 선행 저장이 차단된 것입니다. InputSettings 객체는 아직 원래 ID를 유지하며 프로세스 종료 후 동일 ID 유지가 불가능하다는 기존 한계는 그대로입니다.
