# 589 실제 입력 연결 — 참조/지지 조각 일부 연결, GPU 면적 입력은 미완료

실제 저장 포즈의 작은 입력 구간을 588에 연결했습니다. 제품 입력과 다른 알파나 깊이를 제품 검증으로 취급하지 않았습니다. **실제 GPU 연속 면적 정확도 gate는 미통과이며 제품 소스는 바꾸지 않았습니다.** 587의 179.4MiB 경로도 재적용하지 않았습니다.

## 실제 경로에서 필요한 두 입력

`EyeRenderer367.Samples.RecordRenderGraph`의 이벤트 550은 원본 현재 변형 메시를 같은 카메라 crop으로 그립니다. S0=얼굴 피부 submesh3, S1=흰자4, S2=홍채1, S3=아이라인6, S5=눈썹5, S6=몸 submesh0~3입니다. 각 레이어의 RGBA/META/POINT/UV 및 depth는 실제 4×4 표본이며, 같은 레이어의 알파를 통과한 최근접 조각만 남습니다. `EyeSurface348.shader`와 `EyeSkin348.shader`의 `Eye333Fragment`가 UV 변환·텍스처 필터·알파 분기·깊이·원본 primitive를 만듭니다.

이벤트 551의 `EyeRenderer367.Dispatch → EyeFeature348.compute.Sample583`에서는 다음이 별도 결정입니다.

1. 각 레이어에서 최근접 알파 통과 표면을 먼저 확인합니다. 이후 `cov(m)`, 같은 눈 owner, 앞면을 검사합니다. 앞 표면이 부적합하다고 같은 레이어 뒤 표면을 빌리지 않습니다.
2. **분류 참조**는 S0→S1→S2→S3 중 처음 유효한 표면입니다. 이 표면의 rest u/v로 곡선 띠를 분류합니다.
3. **속눈썹 지지**는 S0, 없으면 S3입니다. 참조가 S1이어도 지지는 S3일 수 있습니다. 속눈썹은 지지 표면의 깊이로 같은 시선 가림을 계산합니다. 참조 u/v와 지지 깊이를 하나의 원본 삼각형으로 강제하면 계약을 잃습니다.
4. HairMETA(영역 모드에서는 논리 셀별 패킷), S5 눈썹, S6 몸을 그 지지 깊이와 비교합니다. 앞쪽 헤어·눈썹은 투과율을 곱하고 몸은 0으로 만듭니다.
5. 현재 `LashAllocated583`은 4×4 지지 합으로 A를 만들고 N=floor(A+0.5)를 적용합니다. 이번 연결은 제품의 이 단계에 들어가지 않았습니다.

| 정보 | 기존 원본/준비 단계에 존재 | 4×4 결과 이후 상태 |
|---|---|---|
| 삼각형 연결·현재 위치·rest·UV·owner·재질/draw 순서 | `EyeFeature348.sampleFace`, 현재 body outputs, 재질 배열에 있음. 저장585 투영표에도 있음 | 최근접 표본만으로 전체/숨은 조각과 경계를 복원할 수 없음 |
| 재질 UV ST·UV 애니메이션·색 알파·cutoff·모드 | 원본/복제 재질과 shader에 있음 | 결과 알파만으로 필터 이전 정보를 역산할 수 없음 |
| 텍스처 원본 알파·필터·밉·wrap·실행 품질 | 원본 Texture2D와 런타임 설정에서 조회 가능 | 표본 사이 통과 경계·필터 footprint·quad 미분값은 저장되지 않음 |
| 참조 표면 ID와 지지 표면 ID/깊이 | 모든 입력이 있으면 같은 우선순위로 다시 구성 가능 | 선택된 결과의 support만으로 분류 참조와 전체 연속 대응을 복원할 수 없음 |
| 헤어 패킷의 셀별 깊이·알파 | 기존 HairMETA에 있음 | 이 계약의 입력으로 재사용 가능. 새 native hair 기하로 바꾸지 않음 |

따라서 원본 정보 전체가 사라진 것은 아닙니다. **4×4 표본에서 역복원할 것이 아니라 원본 준비 단계에서 연속 조각과 참조/지지 대응을 전달해야 합니다.** 다만 실제 GPU 필터의 연속 통과 영역과 수치 오차 경계는 현재 데이터가 그대로 제공하지 않습니다.

## 실제 필터와 알파 함수 확인

공식 Unity 연결의 읽기 조회가 성공했습니다. 7개 텍스처의 알파 바이트 SHA256은 VRM에서 읽은 기존 데이터와 모두 일치했습니다. ARGB32, 밉1, Bilinear, aniso1, Repeat입니다. 실제 품질은 `ForceEnable`, API는 Direct3D11입니다. 이 기록은 바이트와 설정의 일치이며 연속 GPU 알파 경계의 일치 증명이 아닙니다.

설치된 MToon의 `GetMToonGeometry_Alpha`는 MASK일 때 다음 **half 및 quad 미분 연산**을 실행합니다.

`tmpAlpha = (rawAlpha - cutoff) / max(fwidth(rawAlpha), 0.00001) + 0.5; clip(tmpAlpha - cutoff); return 1;`

이번 재질의 cutoff=0.5이면 이상적인 실수 연산에서는 부호 판정이 rawAlpha≥0.5와 같습니다. 따라서 fwidth가 이번 누락의 원인이라고 단정하지 않습니다. half 반올림, 실제 필터/미분 footprint와 투영 오차까지 같은지 증명한 것은 아닙니다. BLEND는 `clip(alpha-EPSILON_FP16)` 후 원래 알파를 반환하므로 아이라인·홍채·눈썹을 모두 불투명 cutout으로 취급할 수도 없습니다. UV ST는 이번 저장 포즈에서 identity이고 UV 이동·회전 속도는 0입니다.

특히 **ForceEnable 상태에서 텍스처의 aniso1만 읽고 임의의 2-texel halo를 실제 GPU footprint의 상한이라고 선언하지 않았습니다.** 아래 연결의 halo는 조건부 입력 검사에만 쓰며 GPU 정확도 경계를 뜻하지 않습니다. 586의 필터 잔차 15표본도 해결됐다고 세지 않았습니다.

## 작은 실제 입력을 588에 연결한 실행

입력은 기존 Geometry2의 첫 저장 포즈, yaw127.000046°, Walk phase0.70000434입니다. 새 촬영은 없습니다. 저장 포즈에서 기존 4×4 지지가 가장 큰 셀을 자동 선택했으며 관측 위치는 (225,52)입니다. 좌표·프레임을 알고리즘 조건에 사용하지 않았습니다.

`connect589.py`는 해당 셀의 실제 투영 삼각형 132개와 재질을 읽었습니다. 알파 범위를 확인할 수 있는 조각은 최근접/앞면/owner 후 참조 우선순위와 지지 우선순위를 따로 구성합니다. 불확실한 상위 조각을 건너뛰고 뒤 조각을 확정하지 않도록 해당 도메인은 미확정으로 뺍니다. 참조 u/v와 지지 z를 명시적으로 교차한 조각을 기존 588에 전달합니다. 새 렌더러나 이미지 격자는 만들지 않았습니다.

연결 가능한 조각은 48개였고 실제로는 모두 **S0 참조/S0 지지**였습니다. S3의 부분 투명 경계가 미확정이므로, S1 참조/S3 지지 fallback이 실제 입력에서 통과했다고 세지 않았습니다. 42개의 알파 미확정 삼각형은 S2 19개와 S3 23개입니다.

상·하한 표의 숫자는 **저장 투영 계수와 제한된 알파 도메인을 입력으로 놓았을 때의 결과**입니다. 임의 halo와 저장 투영 오차가 실제 GPU를 포함한다고 증명하지 못했으므로 실제 GPU 연속 면적의 오차 범위라고 표시하지 않습니다. 11점 대조는 원래 4×4 GPU 기록과의 점 검증이며 표본 사이 면적을 증명하지 않습니다. 해당 셀만의 값으로 전체 눈 N이나9포즈/애니메이션 통과를 판정하지 않았습니다.

추가 GPU 텍스처·제품 readback·새 이미지·실제 회전은 0입니다. CPU/프레임 할당과 GPU 시간은 미측정입니다. 기존 원본 자료를 재사용했으며 큰 버퍼를 복제하지 않았습니다. 20초 유리수 진단 공급기를 런타임에 넣지 않습니다.

## 최소 수정 범위와 진행 판단

현재 작성된 것은 작업공간의 **입력 연결 프로토타입과 읽기 조회**입니다. 제품 변경은 없습니다. 실제 제품 연결을 한다면 최소 책임은 아래와 같습니다. 새 대형 렌더러가 필수라고 결론 내리지는 않았습니다.

- `EyeFeature348.cs`: 기존 sampleFace/body/material에서 불변 topology·rest·UV·재질 정보를 재사용하고, 포즈별 투영/깊이/앞면과 두 눈의 참조·지지 입력 수명을 관리합니다. 큰 다중 고해상도 RT 대신 작은 A_lower/A_upper/valid 출력 수명이 필요합니다.
- `EyeRenderer367.cs`: 기존 Samples550과 Evaluate551 사이에서 면적 집계·상하한 결과를 같은 command 흐름으로 연결해야 합니다. CPU 진단 readback을 제품 경로로 가져오지 않습니다.
- `EyeFeature348.compute`: 기존 N/rank·홍채·흰자·색·합성을 유지하고, 검증된 면적 입력과 유효성만 받는 위치가 `LashAllocated583`입니다. 미확정 입력을 0으로 넘기는 연결은 금지합니다.
- 기존 원본 삼각형/반평면 기능을 이용하는 작은 면적 kernel(가칭 `EyeAreaBounds589.compute`, 아직 미작성)은 필요하지만 **유리수 Python 코드를 그대로 이식하는 것은 성능 해법이 아닙니다.** GPU 수치와 실제 알파 도메인의 상하한 공급 계약이 먼저 필요합니다.
- `EyeSurface348.shader`/`EyeSkin348.shader`는 당장 수정하지 않았습니다. 실제 알파·미분/primitive 입력을 노출해야 한다면 이 두 원본 pass가 책임 위치입니다. 두 셰이더가 다른 alpha 함수를 쓰는 상태에서 면적 kernel만 독립 근사하는 경로는 제품 정확도 검증이 될 수 없습니다.

선택지는 두 가지이며 이번에는 어느 것도 추가 구현하지 않습니다. **현재 GPU 필터를 보존**하려면 실제 sampler/quad/half/투영 오차를 포함하는 경계 공급과 GPU 수치·비용 검증이 필요합니다. 기존 원본 자료는 재사용 가능하지만 이번 halo 결과는 그 보장이 아닙니다. **분석 가능한 공통 알파 정의로 원본 eye source와 면적을 함께 맞추는 변경**은 입력 일관성을 만들 수 있으나 기존 시각/필터 동작 자체의 변경이므로 별도 디자인·GPU 회귀 gate가 필요합니다. 이를 기존 경로와 동등한 정확도 교체라고 부를 수 없습니다.

이번 작은 실제 구간은 정확도 기준과 실시간 비용을 충족하지 못했습니다. 따라서 제품 연결을 확장하지 않고 입력 계약의 부족을 체크포인트로 남깁니다. 실제9포즈·인접 회전·세 방향·전신 영상은 새로 실행하지 않았습니다. 기존 홍채/흰자 소스는 보존했습니다. 마지막 직접 상태는 Edit clean, iris/lash/head/clothes OFF, captureDelta0이며 사용자 설정 해시도 보존했습니다. 메인.html의 영상은 여전히 기존583 비교입니다.
