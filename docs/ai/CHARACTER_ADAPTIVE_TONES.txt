Unity 캐릭터 적응형 명암 시험 — 2026-09-08

결과
- 웹/Python 픽셀 알고리즘의 수학을 이용한 실시간 GPU 시험 경로를 기존 Chibi에 연결했습니다.
- PNG를 프레임마다 Python으로 보내거나 이미지를 다시 생성하는 방식이 아닙니다.
- 최종 아트 승인 전 시험 구현입니다. 원본 모델·눈 이미지·재질·본·Animator·이동·2px 격자·외곽선·깊이는 보존합니다.
- 현재 PC_Renderer / Character Silhouette Outline의 Adaptive Tones와
  PersistentGameplayShell의 CharacterSilhouettePlayerVisual / Adaptive Tone Experiment가 켜져 있습니다.

실제 처리
  기존 표면 색/텍스처 + 무광 연속 명암을 원본 화면 해상도로 별도 렌더
  → 캐릭터 ID / 기존 눈·눈썹·헤어·피부 ID + Oklab 색상 계열로 구분
  → 각 구분의 실제 밝기 범위·분포·공간 대비 분석
  → 관측된 원본 색 후보로 1차원 DP, 허용 오차와 대비를 만족하는 단계 수 탐색
  → 근거가 있는 밝은 영역에만 밝음 후보를 추가
  → 기존 셀 중앙 RGB만 교체 → 기존 외곽선·가림·깊이 합성

따라서 '모든 부위 무조건 3색'이나 전역 평균색 필터가 아닙니다.
색 후보는 실제 입력 픽셀에서 선택하며, 단계 수는 입력 분포에 따라 달라집니다.
추가 카메라·새 Player·새 애니메이션 시스템을 만들지 않습니다.

조절 위치: Assets/Settings/PC_Renderer.asset → Character Silhouette Outline → Adaptive Tones
- toneError = .06: Oklab L의 허용 RMS 오차. 낮을수록 보통 더 많은 단계가 필요합니다.
- chromaError = .06: L로 정규화한 a/b 색상 계열의 격자 폭 기준. 색을 얼마나 분리할지 정합니다.
- contrastRetention = .65: 감지한 넓은 밝음/어둠 영역 사이 대비의 유지 비율.
- minimumContrast = .025: 넓은 공간 명암 보호를 시작하는 최소 대비.
- highlightMinimumContrast = .025: 밝음 후보를 채택하는 최소 대비.
- 숫자는 현재 시험값이며 자동 이미지별 최적 수치 추정이나 확정된 아트 기준이 아닙니다.

비교 / 원복
- 기존 방식: 위 Adaptive Tones.enabled와 Player subject의 Adaptive Tone Experiment를 모두 끕니다.
- 연속 명암 입력: subject만 켜고 Adaptive Tones.enabled를 끕니다.
- 새 단계화: 둘 다 켭니다. 현재 저장 상태입니다. 하나의 셀 캐릭터만 opt-in 가능합니다.
- 기본 전체화면 PIXEL-01은 여전히 꺼져 있습니다. 다른 캐릭터는 기존 경로입니다.

Python판과 동일하지 않은 부분 (숨기지 말 것)
- 기준 소스: LocalOnly/PerfectPixelPalette_20260906, commit 2f99f6a의
  continuous / spatial_steps / highlight_accents 수학. 해당 Python 코드는 이번에 바꾸지 않았습니다.
- GPU는 연결된 색 영역 대신 부위 ID + 고정된 정규화 색상 격자를 사용합니다.
  떨어진 같은 색 부위가 통계를 공유할 수 있고, 격자 경계 근처 색은 과하게 분리될 수 있습니다.
- 실제 전체 색 대신 범위 적응형 32-bin histogram과 각 bin의 관측색 후보를 사용합니다.
- Gaussian 다중 스케일 지원 대신 4×4 → 2×2 공간 타일의 평균·분산·겹침을 사용합니다.
- 현재 사진에서는 머리카락의 약한 밝음 명암이 제거됩니다. 원본 웹 최종본과 같은 완성도로 간주하지 않습니다.
- 프레임 사이 팔레트 고정/시간 누적/깜빡임 방지 처리는 없습니다. 움직임 안정성·다중 캐릭터·빌드는 미검증입니다.
- 1 subject, 160 색 그룹, 입력 4,194,304 pixel의 GPU 자원 상한입니다. 분할 크기를 이 수치로 강제하는 것이 아닙니다.
  상한 초과 등에는 상태 비트를 남기고 원본 셀 색을 유지합니다. 성공으로 숨기지 않습니다.

확인한 것
- Unity 6000.5.9f1 / URP 17.5 / D3D11 / RTX 2080 Ti에서 shader 및 7 compute kernel 컴파일 성공.
- 합성 GPU 7 case: 6개 전체 통과. four_observed_levels는 K=4·RGB·깊이·메타 보존 통과,
  보고 RMS만 엄격 기준 3e-5에서 실패했습니다. 실제값 약6e-8 / 보고값9.16e-5이며
  float prefix moment 상쇄 오차 범위 안입니다. 실패 기록을 지우거나 허용치를 올리지 않았습니다.
  현재 .06 및 시험 .001의 단계 판정은 같지만, 매우 작은 오차 기준의 정확한 판정은 보장하지 않습니다.
- 실제 RGBAHalf 색 / RGBA32 ID 형식의 broad_gradient 추가 1 case 통과.
- 실제 Player 동일 프레임의 정면/45도 × 기존/연속입력/적응형 6장 캡처.
- 같은 Player/Camera entity, 위치, 프레임, material 참조, 2px 유지 및 임시 조명/카메라 복원 확인.
- 실제 게임 936×857 프레임에서 GPU 상태 global=0, READY group=6, 그중 공간 대비 보호=1.
- frame 5869의 추가 compute 7단계 합: GPU .354304ms / CPU .0555ms / inline CPU .0103ms.
  단일 측정이며 원본용 추가 raster·합성·전체 프레임 비용은 포함하지 않습니다. FPS 보증이 아닙니다.
- 최종 shader 오류/경고 0. Console에는 과거 과대 컴파일 작업을 중단한 오류 4건을 그대로 남겼습니다.
- 종료 시 Play off, 임시 background=false, profiler off, 원래 GameMap1 유지. 저장된 시험 스위치는 on.

구현 주의 / 근거
- 원본 native raster와 희소 셀 source는 별개입니다. 비어 있는 셀에서 분석하면 안 됩니다.
- 그룹 통계와 출력은 GPU RenderGraph transient 자원입니다. 정상 프레임의 CPU readback은 없습니다.
- FXC가 큰 루프를 펼쳐 컴파일 메모리가 급증했으므로 [fastopt][loop]로 유지합니다.
  이전 요청이 타임아웃돼도 Editor 내부 컴파일은 계속될 수 있으므로 import 전에 반복 요청하지 않습니다.
- HLSL loop: https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-for
- Oklab: https://bottosson.github.io/posts/oklab/
- URP compute: https://docs.unity3d.com/6000.0/Documentation/Manual/urp/render-graph-compute-shader-run.html
