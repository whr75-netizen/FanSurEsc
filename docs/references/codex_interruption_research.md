# Astra Ultra 게임 개발 신뢰성 — 사용자 보고·원인·실행 계약

조사일: 2026-09-27. 사용자 요청은 질문 직후 종료 반복의 원인 조사와 **미완료 건물 작업 마무리**다. 이 문서 작성이나 지침 검사 통과를 건물 완성으로 바꾸지 않는다. 실제 건물 제작 결과는 해당 아트 연구와 B33 실행 증거가 담당한다.

## 현재 결정 — 문구 보강이 아니라 요구와 실행의 권위 분리

사용자는 B33 수정본까지 거절했다. 질문 직후 종료가 다시 발생했고, 원본 PerfectPixel 자동 추정 대신 슬롯에 맞춘 강제 축소가 계속됐다. 아래의 종전 지침 변경만으로 문제가 해결됐다는 주장은 철회한다. 최신 요청은 개별 외형 보정 대신 모델 리뷰와 전체 게임 개발 운영 방식의 재검토다. 기존 건물은 보존하며 이번 운영 교정의 완료를 건물 완성으로 바꾸지 않는다.

### 공식 설명과 적용 범위

[OpenAI, Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)(9/11)는 누적된 지침/과도한 스킬 선택을 점검하고, 필요한 문서만 연결하며, 과도한 테스트와 이른 검토 대기를 줄이도록 안내한다. 그래서 루트 지침의 반복적인 운영 설명을 줄이고 해당 작업의 절차는 playbook으로 보낸다. 게임 불변조건이나 사용자 요구를 삭제하라는 뜻으로 확대하지 않는다.

[공식 게임 제작 사례](https://developers.openai.com/blog/how-to-build-games-with-astra)(9/4)는 먼저 컨셉아트를 시각 기준으로 저장한 뒤 실제 시스템/플레이 관측과 연결한다. 채택할 것은 기준 화면과 제작 계약의 선행이지, Three.js 시연으로 Unity 정규 픽셀 제작이 검증됐다는 주장이 아니다.

### 이번 프로젝트에서 확인한 원인

1. **원래 문제를 다른 계산으로 바꿨다.** 사용자는 원본 픽셀 격자를 복원하라고 했지만 B33은 슬롯/PPU에서 목표 크기를 역산했다. 수식이 맞아도 정규화 요구를 충족하지 않는다.
2. **대리 지표를 과대 해석했다.** 원본 RGB 일부 일치와 출력 texel 2px 표시는 작은 특징 보존이나 방향 일치의 증거가 아니다. 이 조건만 가진 그래프의 완료는 전체 납품 완료가 아니다.
3. **최종 질문을 계속 의무화했다.** 직전 교정 뒤에도 AGENTS의 '한 번 요청한다'가 남았다. 최신 사용자 정정에 맞춰 형식적 만족도 질문 의무를 없앴다. 앱 엔진이 자동 종료했다는 로그는 확보하지 않았다.
4. **실패 뒤 같은 제작 전제를 재사용했다.** 64×64를 가변 크기로 바꿨지만 입력 격자를 무시하는 축소 전제는 그대로였다. 원인 단계가 아닌 다음 단계의 수치 수선이었다.

### 운영 방식 재구성

- **지침:** 게임/동일 객체/저장/파일 안전 계약은 보존한다. 운영 중복은 줄이고, playbook §1.6의 `요구 → 반례 → 원본/템플릿 → 처음 어긋난 단계 → 허용 변경 → 원래 증상 확인`으로 묶는다. 없는 정보의 필수 질문과 형식적 만족도 질문을 분리한다.
- **알고리즘:** 원본 PerfectPixel 공개 API의 자동 검출을 실제 실행한다. AI가 목표 폭/높이/PPU/축소율을 주입하는 CLI가 없다. 입력/엔진/출력 해시와 실제 격자 좌표를 보존한다.
- **제작 진입점:** 기존 B33 강제 축소 스크립트와 Unity Build/Apply를 퇴역 처리한다. 현재 씬/원본/과거 결과/Inspect는 보존한다. 새로운 생성/배치는 전체 기준 아트와 실제 템플릿/투영 연결 없이는 준비 완료가 아니다.
- **기계 확인:** 이전 강제 manifest 거절, 자동 격자 원본 산출 확인, 필수 입력 없는 생성/배치 거절을 실제 파일로 확인한다. AI의 승인 boolean이나 파일 존재만으로 통과하지 않는다.
- **정직한 범위:** 이번 변경은 로컬 운영 경계와 확인된 입력 변환 오류를 고친다. 생성형 모델의 디자인 일관성, 모든 버그, Codex 호스트의 final/압축/서버를 수리했다는 뜻이 아니다. 모델 스왑/추론 강도 조정은 검증 없는 해결책으로 적용하지 않는다.

## 종전 조사 — 참고용, 해결 선언 아님

- **공식 모델 행동 설명이 있다.** OpenAI는 GPT-6 Astra가 확인 질문을 더 자주 하여 합리적 가정을 하고 계속할 상황에서도 멈출 수 있고, skills/AGENTS 같은 파일의 모호하거나 충돌하는 지침에 민감할 수 있다고 설명한다. 허용된 작업을 먼저 수행해 검토 가능한 구체 결과를 준비하고 요청을 끝까지 이행하도록 안내한다. 이는 현재 상위 지속 수행 지침과도 일치한다. Ultra만의 결함 또는 이번 서버 장애를 입증하지는 않는다. [공식 Model guidance의 Initiative and follow-through / Instruction following](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)
- **다른 사용자도 유사 중단을 보고했다.** 아래 이슈는 질문을 완료 상태로 표시하는 현상, 진행 메시지 뒤 종료, 압축 뒤 종료, 빈 정상 응답이라는 서로 다른 증상이다. 동일한 뿌리 원인으로 합치지 않는다.
- **이번 프로젝트에는 직접 확인 가능한 로컬 원인이 있다.** 광범위한 시각 승인 문구를 중간 산출물마다 적용했고, B31 review에는 수정으로 이어지는 길이 없었으며, B32에서는 부모 제작 목표가 실험 목표로 축소됐다. 마지막 것은 직전 종료에 대한 강한 직접 증거다. 서버/연결 장애나 컨텍스트 초과 로그는 이번 감사에서 확인하지 않았다.

## 종전 적용 결정과 실패한 부분

1. **종전 교정은 불충분했다.** §2의 부모/하위 목표 분리는 유효하지만 §5에 최종 피드백 질문 의무를 남겨 같은 현상이 반복됐다. 현재 결정은 위 절을 따른다.
2. **WorkLoop의 question 의미를 명시한다.** 작업 인계는 같은 요청에서 수행→submit→후속 노드로 연결한다. 기존 B31/32 실행 기록이나 runtime engine을 바꾸어 과거 결과를 완료로 승격하지 않는다.
3. **B33은 실제 부모 목표를 유지한다.** 개별 자산 → 도면·표시·명암 통합 → 실제 기지 관측 → 수치 판정까지 연결한다. 기술 실패는 측정 근거를 통합 노드에 전달하여 한 번 제한 수선한다. 최종 기술 결과와 미술 승인 pending을 분리한다. 실제 사용자 답변을 다시 무조건 blocked로 보내는 review 노드를 두지 않는다.
4. **같은 지속 수행 문구를 계속 누적하지 않는다.** 현재 상위 지침에는 이미 자율 진행 계약이 있다. 필요한 것은 로컬 문구의 범위 정리와 실제 남은 작업의 수행이다. 모델 교체·전역 설정 변경·무한 재시도 프로그램은 이번 조사로 정당화되지 않는다.

실행 계약과 관측 schema: [B33 README](../../Tools/Building33/README.md). 지침 검사 통과는 문서 정합성만 의미한다. 실제 작업을 끝까지 수행했는지와 미술 수준이 적합한지는 B33 산출물·실제 사용자 피드백으로 별도 판정한다.

## 미해결·재개 조건

모든 조기 종료가 로컬 계약 탓이었다고 단정하지 않는다. 이후 같은 일이 생기면 해당 턴의 실제 이벤트를 다음과 같이 구분한다.

- 질문이 final 본문에만 있고 앱이 완료로 표시했다면 #41140과 비교한다.
- 진행 메시지 뒤 예정 도구 호출이 없고 오류/취소도 없다면 #46153과 비교한다.
- `context_compacted` 바로 뒤에 종료된 실제 이벤트가 있으면 #16042와 비교한다. 대화가 길다는 사실만으로 해당하지 않는다. [공식 Compaction 문서](https://developers.openai.com/api/docs/guides/compaction)는 압축한 상태로 후속 호출을 이어 가는 흐름을 설명한다.
- HTTP200/정상 stop인데 본문이 비었다면 #32389의 구체 signature와 비교한다.
- disconnect/timeout/incomplete response/HTTP 오류가 있다면 연결·서비스 장애로 따로 조사한다.

현재는 질문 도구의 비동기 이벤트 원문이나 서버 진단 로그를 확보하지 않았으므로 그 계층의 동일 버그 여부는 미확정이다. 이 불확실성은 이미 승인된 건물 제작을 멈출 이유가 아니다.
