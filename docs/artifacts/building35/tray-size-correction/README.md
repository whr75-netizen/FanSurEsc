# 사과 트레이 실물 치수·면 투영 최소 실험

상태: 최소 실험을 실행했으나 **Unity 통합은 거절했습니다**. 면 투영 결과72×48에서 기존 그림의 사과가 약13~15cm로 커져 전체 확대만으로 실물 비례를 맞출 수 없었습니다. 실제 계산은 `fruit-size-estimate.json`, 결정은 `experiment-decision.json`에 보존했습니다. 뒤이어 빈 상자와 사과를 분리한 [최종 합성](../tray-composite/delivery-result.json)으로 기존 세 트레이만 교정했으며, 다른 승인 가구는 유지했습니다. 아래는 이 실험의 입력 계약입니다.

## 원인과 크기 소유자

기존 `flat_prop`는 사과까지 포함한 그림 전체의 표시 높이 .25m로 화면 크기를 정했습니다. 그 값은 배치의 .6×.45m footprint와 연결되어 있지 않았습니다. 새 실험은 `Tools/Building35/metric-catalog.json`의 폭X .4m, 깊이Z .3m, 목재 벽 높이 .1m와 공통127px/m를 사용합니다. World Transform scale이나 PNG bbox 높이가 실물 크기의 소유자가 아닙니다.

40×30×10cm는 [Gadsby Acacia Wooden Crate 공식 제품 치수](https://www.gadsby.co.uk/products/acacia-wooden-crate-40-x-30-x-10)에서 확인한 크기 후보입니다. 특정 실물의 규격이며 모든 사과 상자의 보편 규격은 아닙니다. 최종 값은 담당 작업의 metric catalog가 소유합니다.

## 실제 source 표식

입력은 보존된 `docs/artifacts/building35/native/produce/native.png`, 198×164입니다. 좌상 texel 중심=(0,0), x오른쪽/y아래입니다. 기둥/테두리가 보이는 여섯 점과 과일에 가려진 한 점을 분리했습니다. 상세 좌표·source SHA256은 `source-corners-proposal.json`에 있습니다.

- 관찰: 좌측 위/아래 `(20,82)/(20,108)`, 앞쪽 위/아래 `(82,121)/(82,147)`, 우측 위/아래 `(181,79)/(181,107)`.
- 추정: 뒤 위 `(106.5,35.75)`. 왼쪽 뒤 테두리의 `(30,74)→(62,58)`, 오른쪽 뒤 테두리의 `(143,54)→(167,66)` 직선을 연장한 교점입니다. 가려진 모서리를 보았다는 뜻이 아닙니다.
- 앞 세 점을 평행사변형으로 완성하면 뒤 점은 `(119,40)`입니다. 두 방식의 차이 12.5px/4.25px를 숨기지 않습니다. 생성 그림의 면 표식·기울기 불일치가 남아 있으며, 교점 추정에 대한 확신이나 미술 합격으로 대체하지 않습니다.
- source의 실제 모서리에도 두꺼운 cap·검은 윤곽선이 있어 1~2 native px 표식 불확실성이 있습니다. 뒤점은 약5px 이상의 불확실성을 고려해야 합니다.

사용하는 세 면은 목재 Xmin, 목재 Zmin, 테두리 안의 top painted contents입니다. 하나의 bbox billboard를 돌려서 세 면이 맞았다고 하지 않습니다. 세 면은 같은 canonical 꼭짓점을 공유하며 목표 바닥 축 기울기는 ±.5, 수직은 dx=0입니다.

## 과일 크기와 정보 한계

서로 구분되는 붉은 사과 몸체는 약7개가 보입니다. 생성 프롬프트의 '8개'를 실제 개수로 보고하지 않습니다. 앞 사과 bbox 후보 `[61,88,105,120)`(44×32), 뒤 사과 `[84,38,126,68)`(42×30)를 남겼습니다. 줄기·별도 잎을 제외한 몸체의 시각 표식이며, 다른 사과와 가려지는 하단 경계는 2~3px 불확실성이 있습니다.

catalog의 70~95mm 직경 참고는 공통127px/m에서 8.89~12.065px에 해당합니다. 다만 이는 해당 방향에서 직경을 읽을 수 있을 때의 단위 환산이며, 기울어진 top면에 그려진 사과 bbox를 곧 구의 실제 직경으로 삼는 검사가 아닙니다. 현재 바구니를 전체 확대하면 이미 적정 크기에 가까웠던 사과도 함께 커질 수 있습니다.

단순 포장 가능성만 계산하면 70~80mm 사과 3~4개 길이는 .21~.32m입니다. .4×.3m 바구니에서 이 정도 열과 가장자리 여유가 가능한지 비교할 수 있습니다. 예를 들어 판재 두께를 **가정**한 내부 .36×.26m에는 80mm 사과 4×3개가 기하학적으로 들어갑니다. 이것은 실제 제품 내부 치수나 현재 그림의 사과가 그 규격이라는 증거가 아닙니다. 여유·포개짐·개별 사과 지름을 전체 이미지의 크기로 동시에 조절할 수는 없습니다.

최소 실험에서는 과일이 Y=.1 top면에 그려진 내용물입니다. 구형 체적·돌출 높이·가려진 사과 면은 복원하지 않습니다. source 바깥으로 솟은 잎/과일은 기존 nearest-plane outline 외삽으로 XZ footprint 밖에 갈 수 있으므로 receipt의 실제 bounds와 첫 출력에서 확인해야 합니다. 목재면 투영이 맞았다고 이 표현까지 합격하는 것은 아닙니다.

## 실행과 반환

담당 그래프 명령: `python -B Tools/Building35/tray-prepare.py`. 기존 NumPy/Pillow deps와 `project_faces.project()`를 그대로 재사용합니다. 기존 함수의 alpha>=128·binary-alpha 정책도 바꾸지 않습니다. source를 다시 PerfectPixel에 넣거나 생성하지 않습니다.

출력은 이 폴더의 `appletray_metric/{native.png,positions.rgba32f,face-id.png,spec.json,receipt.json}`과 `production-manifest.json`입니다. 기존 실험 출력이 있으면 덮지 않고 중단합니다. 생성된 manifest의 상태는 실험이며 자동 미술 합격이나 Unity 삽입 권한 판정이 아닙니다.

첫 출력에서 목재 방향·크기·과일 body bbox를 같이 비교합니다. 실물 상자의 크기와 과일 직경을 동시에 충족하지 못하면 그대로 통합하지 않습니다. 다음 후보는 기존 목재 틀과 독립 .08~.09m 사과 sprite를 지지점에 조합하는 방식입니다. 이번 작업에서는 그 후속 생성이나 분해를 실행하지 않았습니다.
