### A30-3 제한적 랜덤 생성의 설계 제안

현재 가장 작은 확장안은 **저작된 유형/평면 규칙 + 제약을 만족하는 범위의 매개변수 변형**이다. 기존3상가/공용2층 구조를 작은 실험의 기준으로 보존하고, 서로 다른 영업·생활 연결을 실제 데이터 항목으로 추가한다. 새 범용 최적화기는 그 템플릿이 표현하지 못하는 외곽/복합 구조가 확인됐을 때 대조한다.

```mermaid
flowchart LR
    P[POI 공간 프로그램·용량] --> S[부지·동·층·코어 예약]
    S --> G[필수/허용 연결 그래프]
    G --> R[실제 치수 방·복도·개구부]
    R --> F[가구·설비·사용/파밍 슬롯]
    F --> V[통행·연결·수용량 판정]
    V --> A[확정 구조에서 기존 메시·아트 배치]
```

1. 프로그램 데이터는 `programId/variantId`, 필수/선택 방, 객실·좌석·작업 인원 범위, 필수/금지 연결, 고객/직원/주거 구역, 외부 납품/보행 연결, 층·계단 코어와 가구 사용 영역을 가진다. 부지에서 모텔 동·주차·수영장/데크 소속과 접근 관계를 풀고 실내 방 목록에 주차장을 억지로 끼우지 않는다.
2. 랜덤 변수는 허용 출입 variant, 동등한 좌우 배치, 방 폭/깊이 범위, 적합한 객실/선반 반복 개수, 지정된 코어 후보와 선택 소품이다. WC·필수 계단·서비스 동선·필수 설비를 확률로 누락하지 않는다. 대칭 변형도 방 역할/출입/설비를 함께 변환한다. 원본 sprite를 늘려 평면을 맞추지 않는다.
3. 난수 범위는 `hash(seed, stableBuildingId, variantId, stageId)`로 나누는 제안이다. 방 하나의 변경이 다른 건물 전체를 바꾸지 않게 한다. seed/version과 확정 구조를 함께 저장해 재현/모딩 자료로 사용한다. 저장 경로/런타임 구현은 아직 결정하지 않았다.
4. 미터 단위 room rectangle은 포함·최소 폭·면적·비중첩을 만족해야 한다. 필수 인접은 공유 벽과 문폭+양끝 여유가 성립해야 한다. 층간 계단 개구부·참·코어는 같은 계획 원본에서 파생한다. `F=(외곽⊖D(r+m))−∪(장애물⊕D(r+m))`에서 출입구→계단/각 사용 소켓의 연결성을 검사한다. room graph 연결만으로 가구 배치 후 통행을 합격 처리하지 않는다.
5. [CP-SAT 공식 문서](https://developers.google.com/optimization/cp/cp_solver)의 정수 제약은 위 사각형/배정 문제의 구현 후보다. 사용하면 물리 치수의 정수 단위를 먼저 정의하고 feasible/optimal/infeasible/unknown을 구분해야 한다. timeout이나 해 없음은 무제약 방·폭 축소로 덮지 않는다. 현재는 설치하거나 도입하지 않았다.
6. 실패는 `program/parcel/core/room/opening/furniture/connectivity`의 원인 단계로 반환한다. 랜덤 위치 무한 재시도 대신 후보 소진/불가능을 반환하며 마지막에 필요한 구조·이동 관측을 묶는다. 좌표/원본·허용 변경은 실행 중 바꾸지 않는다.

### A30-4 50→150종 확장과 다음 최소 작업

기존50슬롯안은 출발점이다. 10계열×5구조 조건을 실제 저작 항목으로 채우고, 적합한 계열에서 코어·출입·용량·임차 연결 조건을 늘려100~150항목으로 확장할 수 있다는 **설계 제안**이다. 모든 계열에15변형을 강제하지 않는다. 주차/서비스 모듈은 부지 자료로 별도 집계하고, 모텔 같은 숙박 계열의 실제 건물 프로그램을 추가해야 한다. 회전·팔레트·소품 난수·동일 topology의 치수 차이만으로150개의 독립 구조라고 보고하지 않는다.

기록은 `구조 템플릿 수 / 치수·용량 variant 수 / 생성 인스턴스 수 / 아트 kit 수 / 실제 이동 확인 수`로 나눈다. 한 변형에 별도 원화를 모두 새로 만들 필요는 없지만, 기능 부품·창호·계단·설비와 표현 가능한 아트 방향이 있어야 한다.

후속 최소 실험은 다음3종이다. 첫 구현 때 필요한 결과/허용 변경/완료 기준을 별도 확정하고 기존 owner API를 확장한다.

| 대표 | 먼저 드러낼 확장 문제 | 합격 관측 |
|---|---|---|
| 카페8/16석 | 좌석·가구 사용 공간이 방 크기와 함께 증가 | 지정 용량·고객/직원/WC 접근·문/의자 사용 여유 |
| 상가주택 | 공용 코어와 점포/세대 출입·세대 내부 graph 분리 | 점포를 관통하지 않는 주거 출입·거실/주방→침실/WC·층 연결 |
| 2층 모텔+주차+수영장 | Site→동/객실/갤러리/코어→외부 서비스/데크 | 객실 용량·욕실·층간 코어·프런트/보행/주차 소속·데크 연결 |

위 대표의 실제 구조·통행과 아트 배치가 성립한 뒤 라이브러리를 늘린다. 이번에는 설계 항목50개를 저작하거나 랜덤 생성기를 구현하지 않았다.

### A29-1 결론과 현재 부족한 부분

**참고할 실제 도면과 제작 절차는 있다. 다음 문제는 예쁜 외관을 먼저 늘리는 것이 아니라, 서로 다른 생활/영업 구조를 표현할 설계 데이터와 수용량 계약이 부족한 것이다.** 정해진 작은 직사각형에 방 이름과 소품을 배분하는 것만으로는 모텔 단지·다가구·상가주택을 구분하기 어렵다.

이번에 직접 확인한 코드 사실:

| 현재 구현 근거 | 확인한 사실 | 후속 설계가 해결할 문제 |
|---|---|---|
| `Assets/Scripts/WorldGeneration/UrbanArchitecturePlan.cs`, `UrbanArchitecturePlan`, `ParkingParcelIndex` | 건물 평면 목록과 별도의 주차장 필지 하나를 보유 | 여러 동·공용 마당·수영장·해당 건물 주차장의 소속/접근 관계를 가진 부지 원본이 필요 |
| 같은 파일 `BuildFloorPlan` | 경찰·주거는 같은 2층 복도/방 분할을 쓰고 용도별 방 이름을 바꿈 | 주거의 세대 현관→거실→침실/WC와 경찰의 공공/직원 구역은 다른 연결 구조여야 함. 승인된 기존 구조를 이번에 교체하지 않음 |
| `EnterableSpriteBuilding.Commercial.cs`, `PlaceDiningSets` | 테이블＋의자 2개짜리 모듈의 후보가 둘뿐. 최대 2세트/4석이며 공간이 넓어져도 늘지 않음 | 좌석 수가 평면 크기와 설비 개수를 결정하도록 연결 |
| 같은 파일 `PopulateCommercialRoom`, `PlaceShelves` | 창고 선반/직원 책상은 각각 한 번 배치. 판매 선반은 깊이에 따라 행이 증가하지만 좌우 두 띠만 사용 | 방 역할과 목표 재고/좌석/작업 인원에 맞는 설비 수. 충돌 0만으로 기능 충족을 판정하지 않음 |
| `Assets/Prefabs/PersistentGameplayShell.prefab`, CharacterController | 저장된 높이 1.8m, 반경 0.5m | 실건축의 좁은 문을 그대로 복제하면 캐릭터 충돌체와 양립하지 않을 수 있음. 미술 크기와 이동 여유를 구분하며 이번에는 둘 다 변경하지 않음 |

따라서 “캐릭터와 건물을 일괄 확대/축소”하는 수정으로 먼저 결론내리지 않는다. 기존 A28의 12–18m × 10–14m 건물 입력 안에서 원하는 기능이 가능한지부터 계산해야 한다. 실측 비례, 이동 충돌체, 설비 개수, 화면상의 가독성은 각각 별개의 원인이다.

### A29-2 게임 자료: 확인한 제작 방식과 한계

| 대상·1차 자료 | 확인한 내용 | 프로젝트에 적용할 판단 / 증거 한계 |

| **Project Zomboid** — [공식 BuildingEd/WorldEd 소개](https://projectzomboid.com/blog/news/2013/02/hello-hello-we-are-the-modding-tools/), [The Indie Stone 제작진의 TileZed/BuildingEd 가이드](https://theindiestone.com/forums/topic/21951-the-one-stop-tilezed-mapping-shop/) | 방 정의·모양, 문/창문, 가구, 계단과 위층, 지붕을 저작하고 `.tbx` 건물로 저장해 WorldEd에 배치한다. 방 유형은 전리품 분포와 연결된다. 위층을 계단 위에 만들면 바닥 구멍을 처리하며, 외부 지붕에도 실내/외 판정용 방 정의가 필요하다. | **의미를 가진 건물 템플릿과 도시 배치를 분리**하는 실제 작업 경로다. 모든 집을 무작위로 완성하는 범용 자동 설계기의 증거는 아니다. 가이드 자체도 방 크기를 바꾸면 문/창문 위치를 확인하도록 경고한다. 오래된 제작 절차이며 현재 Unity 호환 도구를 설치·실행한 증거는 아님. |
| **Escape from Tarkov** — [RE3MR 제작자의 Customs/Dorms 지도·PSD](https://reemr.se/customs/), [커뮤니티 층별 SVG 지도 원본](https://github.com/the-hideout/tarkov-dev-svg-maps) | 제작자가 배포한 기숙사 지도/편집 원본과 Customs·Streets 등 구조를 읽을 자료가 존재한다. | 방·복도·계단과 층별 이동을 조사할 후속 자료다. **Battlestate의 생성 알고리즘은 공개 확인하지 못했다.** 이번에는 대용량 기숙사 PNG의 내부를 직접 읽지 못했으므로 문 위치·방 개수·실측 치수를 확정하지 않는다. 지도 제작자의 procedural 작업을 게임의 레벨 생성 방식으로 혼동하지 않는다. |
| **NAKWON: LAST PARADISE** — [공식 개발 노트, “NAKWON Note #1: Shopping Mall Map Preview”](https://steamcommunity.com/app/2582960/allnews/) | 개발진은 영등포의 실제 쇼핑몰을 바탕으로 삼고, 원래 시설을 일부 바꿔 생존자 구역·검문·주차장 활용을 구성했다고 설명한다. 탐사 경로, 탈출, 층간 이동, 다층 지도 UI를 함께 설계했다. | **실제 한국 건물의 공간 구조 → 게임 목적에 맞는 경로 재설계**라는 근거다. 이번 조사에서 전체 치수 평면도나 자동 건축 생성 코드는 찾지 못했다. 게임 화면만 보고 내부 알고리즘을 추정 확정하지 않는다. 낙원의 경쟁/보상 규칙을 본 프로젝트의 싱글 PvE 규칙으로 가져오지 않는다. |

좀보이드에서 참고할 것은 방 이름만이 아니라 `건물/층/방 의미 + 문·계단 연결 + 방 용도별 내용물`이다. 타르코프의 기숙사/아파트와 낙원의 쇼핑몰은 서로 다른 유형이므로 한 복도 템플릿의 색상만 바꿔 대체하지 않는다. 게임 자료는 탐사 구조, 실제 건축 자료는 생활·영업 기능과 크기의 근거로 나누어 사용한다.

### A29-3 실제 모텔: 건물 한 채가 아니라 부지 단위

**Caribbean Motel — 미국 의회도서관/NPS의 HABS NJ-1186 조사자료.** [원문 PDF](https://cdn.loc.gov/master/pnp/habshaer/nj/nj1400/nj1486/data/nj1486data.pdf). PDF 7–9쪽 설명과 11쪽의 1958년 배치도를 직접 읽었다. 11쪽 도면은 렌더해 시각 확인했다.

- 2층, 세 면을 이루는 건물 날개, 안뜰의 C자 수영장, 외부 공용 보행 공간, 주차가 결합된 사례다. 동쪽 동은 1층 주차/2층 라운지이며 사무실·객실·세탁실이 서로 다른 부분에 놓인다.
- 내부 중앙 복도 대신 외부에서 객실에 접근한다. 외부 계단과 수영장 쪽에서 위층으로 가는 경사로가 있다. 이것은 해당 건물의 사례이지 모든 모텔에 경사로를 요구하는 규칙이 아니다.
- 보고서의 공용 외부 통로 폭은 6ft ≈ **1.83m**. 안뜰만 약 115×53ft ≈ **35.05×16.15m, 566㎡**다. 이는 현재 최대 18×14m =252㎡인 단일 건물 입력보다 넓다. 모텔을 현재 상가 상자 하나에 축소해 넣는 방식으로 해결되지 않는 구체적인 반례다.
- 1958년 배치도는 부지·건물·수영장·주차 관계를 보여 준다. 모든 객실 욕실의 치수 평면도나 현재 안전 기준을 확인한 것은 아니다.

**San Diego Mission Valley 모텔 — [시청 공개 보고서 HO-15-057](https://www.sandiego.gov/sites/default/files/legacy/development-services/pdf/hearingofficer/reports/2015/HO-15-057.pdf).** 기존 모텔의 항공사진(PDF 7쪽)과 철거 배치도(17쪽)를 직접 렌더해 확인했다. 여러 긴 동과 수영장·차량 통로·주차를 한 부지 안에 구성한 사례다. 자료 후반의 신축 다층 호텔 도면을 기존 2층 모텔 평면도로 혼동하지 않는다. 객실 내부 설계의 근거로 사용하지 않는다.

`[제안]` 모텔 원본의 최소 관계:

```text
접도 → 차량 입구 → 차량 통로 → 주차 구획
     → 보행 입구 → 프런트 → 안뜰/외부 갤러리 → 객실 현관 → 침실＋욕실
                                └→ 계단/참 → 2층 갤러리 → 2층 객실
서비스 접근 → 린넨/세탁/관리 공간
안뜰 보행 → 수영장 주변 데크   (물 영역은 보행 바닥과 별도)
```

수영장 자체를 만들기 전에 데크·갤러리·계단 하부/상부 도착점의 연속성을 예약한다. 객실 반복 모듈, 코너 모듈, 계단 모듈, 프런트/서비스 모듈은 역할이 다르다. 주차 대수·객실 수·수영 가능 여부·출입 정책은 아직 미정이며 임의로 게임 규칙을 추가하지 않는다.

### A29-4 실제 한국 건축: 공용 동선과 세대 내부의 구분

**로지아 Y — 유주헌·제이에이치와이건축사사무소(JHY architects & associates)의 [건축문화 수록 원문 PDF](https://jhy.co.kr/architecture/wp-content/uploads/sites/2/2018/03/j2MxKP7u_EAB1B4ECB695EBACB8ED9994433_EBA19CECA780EC9584Y.pdf).** PDF 3쪽, 인쇄면 048–049의 1/2/3/5/6층 평면과 단면을 렌더해 직접 확인했다.

- 1층은 주차·임대 상가·공용 계단/엘리베이터 접근이 구분된다. 상가 내부를 통과해야만 주거 위층에 들어가는 평면이 아니다.
- 위층의 공용 코어에서 세대 현관에 들어간 뒤 거실/식당/주방과 침실·욕실로 연결된다. **공용 복도에서 모든 침실 문이 직접 열리는 기숙사 구조와 다르다.**
- 층마다 실 배치는 달라도 계단/엘리베이터 코어의 수직 관계는 유지한다. 서로 다른 가족의 주거 요구와 외부 공간을 반영한 사례다.
- 이 사례는 6층 상가주택이며 모든 한국 빌라의 표준 평면이 아니다. 면적이나 층수를 현 프로젝트에 그대로 복제하지 않는다.

보완 사례는 [대한건축사협회 「평택 비전동 근린생활시설 및 주택」](https://kiramonthly.com/844)과 [설계자 AAPA의 「너도나도 집」 자료](https://magazine.brique.co/project/%EB%84%88%EB%8F%84%EB%82%98%EB%8F%84-%EC%A7%91/)다. 전자는 상가/주거 복합과 수직 동선, 후자는 세대마다 수직으로 쓰는 주거 유형의 비교 자료다. 이번에는 본문·도면 게시 여부를 확인했으며 실제 도면 이미지를 판독하지 않았다. “한국 집은 모두 중앙 계단＋좌우 세대” 같은 단일 규칙을 만들 근거로 삼지 않는다.

`[제안]` 공용 계단을 갖는 상가주택/다세대 유형의 의미 계층은 `공용 계단/복도 → 세대 현관 → 세대 공용실 → 개인실/욕실`이다. 공용 계단, 세대 내부 계단, 옥상 출입은 별도 역할로 저장한다. 침실을 통과해야 다른 세대나 공용 옥상에 가는 연결은 해당 유형에서 실패다. 외관의 간판·실외기·벽 재료만 한국식으로 바꾸어 이 구조를 대체하지 않는다.

### A29-5 건축 유형 라이브러리 제안

아래는 자료를 바탕으로 한 **후속 저작 분류**다. 실제 도면 50개를 확보했다거나 구현한 상태가 아니다. 이전 사용자가 상가를 우선했으므로 소매/식당/카페의 수용량 보완을 먼저 실험하고, 모텔·한국식 주거는 서로 다른 구조를 시험할 다음 후보로 둔다.

| 유형 | 필수 공간/연결 | 의미 있는 변형 |
|---|---|---|
| 작은 소매점/편의점 | 입구→판매→계산, 창고/직원/WC, 납품 접근 | 코너 출입, 측면/후면 납품, 단독/연속 점포 |
| 중형 마트 | 판매 구역·가로/세로 통로·계산대·재고/납품·직원 구역 | 선반 열 수, 복수 계산대, 하역 위치 |
| 카페/식당 | 좌석·주문/주방·식자재·WC; 고객/서비스 경로 | 좌석 수, 주방 비중, 테이크아웃형/홀형 |
| 2층 도로변 상가 | 1층 점포, 독립된 위층 출입/계단, 2층 점포/사무실 | 위층 한 임차인/여러 임차인, 측면 계단 |
| 상가주택 | 상가/주거 입구 분리, 공용 코어, 위층 세대 내부 | 주차층, 층당 세대 수, 옥상 접근 |

| 아파트/기숙사 | 공용 코어/복도와 반복 세대/객실 구분 | 편복도/중복도, 계단 수/위치, 공용실; 아파트 세대 내부와 기숙사 객실은 별도 |
| 안뜰형 2층 모텔 | 프런트·객실/욕실·외부 갤러리·계단·서비스·주차·수영장/데크 | ㄱ/ㄷ/분동형, 객실 수, 서비스 동, 주차 접근 |
| 업무/경찰 시설 | 방문객 구역·직원 구역·기록/지원·WC·층 연결 | 공공/직원 출입 구분, 실 조합, 지원 면적 |
| 복합 상업 건물 | 공용 수직 동선·임차 구획·후방 서비스·주차 접근 | 층별 임차 구성, 수직 연결 수, 안뜰/아트리움 여부 |

50개 설계는 예를 들어 위 유형마다 5개의 **서로 다른 연결/용량 조건**을 저작하는 방식으로 관리할 수 있다. 색상, 회전, 무작위 가구 위치만 다른 것은 독립 설계로 세지 않는다. 같은 유형 안에서도 필요 객실·좌석·세대 수가 다르면 치수와 평면이 함께 달라져야 한다.

### A29-6 알고리즘 선택: 템플릿을 계산 가능한 설계로 만들기

| 방법 | 실제 근거 / 적합성 | 이번 판단 |
|---|---|---|
| 의미 있는 평면 템플릿＋치수·수용량 매개변수 | 좀보이드의 건물 저작/재사용 방식과 현재 직교 평면 코드에 가장 가깝다. 역할·필수 연결·최소 치수가 저작되어 있어 실패 이유를 특정하기 쉽다. | **근거리 후속 후보.** 고정 방 이름 배열을 늘리는 대신 부지/세대/수용량 계층을 추가 설계한다. |
| 공간 프로그램 그래프＋제약 탐색 | [Merrell·Schkufza·Koltun 논문](https://www.cs.princeton.edu/courses/archive/spring11/cos598A/pdfs/Merrell10a.pdf)은 방 크기·인접 관계 등 프로그램에서 다층 주거 평면을 구체화한다. [OR-Tools CP-SAT 공식 문서](https://developers.google.com/optimization/cp/cp_solver)는 정수 제약과 해 상태를 구분하는 구현 후보다. | 비정형 필지/여러 용량의 확장 후보. 격자 단위 정수화와 제약을 별도 정의해야 하며 도구 설치·통합은 하지 않았다. 해 없음과 시간 제한 내 미발견을 구분한다. |
| 데이터 기반 가구 배치 | [Henderson·Subr·Ferrari, Automatic Generation of Constrained Furniture Layouts](https://arxiv.org/abs/1711.10939)는 가구의 공동 출현과 관계를 학습해 제약 아래 배치한다. | 임의 흩뿌리기 대신 역할/관계 모델이 필요하다는 근거. 현재는 학습 데이터가 없으므로 정해진 기능·설비 모듈로 먼저 계산한다. 논문을 연결했다고 자연스러운 결과가 보장되지는 않음. |

#### 원본 표현과 수학적 제약 — 모두 설계 제안

1. **계층:** `SitePlan → Building/Wing → Floor → Unit → Room → Fixture`. 단일 점포는 Unit 하나로 표현할 수 있다. 부지는 도로 접점, 차량/보행 접근, 동들의 위치, 주차, 마당/수영장과 소유 관계를 가진다. Room/Opening 이동 그래프는 이 구조에서 파생한다. Mesh/Collider/도면/전리품 소켓은 원본이 아니다.
2. **입력:** 유형, 목표 객실/세대/좌석/설비 수, 필수 인접·분리 관계, 층수 후보, 가구의 실제 점유/사용 공간, 출입 상태, seed. 출처와 `사용자 확정/자료 사실/실험 가정`을 별도 기록한다. 건축 프로그램과 아트 스타일을 섞지 않는다.
3. **좌표:** 기존 건물 로컬 XZ 미터, +Z 정면, +Y 위, root scale=1을 보존한다. 동이 여러 개면 `p_world = T_site · T_wing · p_local`로 변환을 한 번씩 합성한다. 방 모서리별 임의 offset, 화면 픽셀에 맞춘 물리 치수 왜곡으로 해결하지 않는다.
4. **수용량:** 한 테이블 모듈의 좌석이 k개이고 목표 좌석이 S개면 최소 모듈 수는 `ceil(S/k)`다. 테이블·의자를 당겨 쓰는 영역·주 통로가 들어갈 때만 성립한다. 직렬 가구 열의 길이는 가구 폭 합＋간격 합＋끝 여유로 계산한다. 면적만 충분하다고 적합으로 처리하지 않는다.
5. **반복 객실:** 편복도에 객실 한 열이 붙는 날개에서 층별 길이는 `그 층·날개·열의 객실 수 × 벽을 포함한 반복 피치 ＋ 비반복 코어/끝벽 길이`다. 건물 전체 객실 수를 넣지 않는다. 층별 길이와 코어 정렬을 함께 풀어 건물 외곽을 정한다. 깊이는 편복도형이면 `객실열 깊이 ＋ 갤러리 깊이 ＋ 경계벽 두께`, 중복도형이면 `양쪽 객실열 깊이 합 ＋ 복도 깊이 ＋ 경계벽 두께`다. ㄱ/ㄷ자 코너의 중복 영역은 별도 모듈로 처리한다. 주차/데크/차량 통로까지 실제 배치가 성립해야 SitePlan이 적합하다. 총면적 합만 맞추는 검사는 불충분하다.
6. **직교 방:** 각 Rect의 포함과 최소 폭/깊이, 같은 층에서 `x_i+w_i≤x_j OR x_j+w_j≤x_i OR z_i+d_i≤z_j OR z_j+d_j≤z_i`를 만족시킨다. 연결이 필요한 두 방은 유효한 공통 경계를 가져야 하고, 그 경계가 문폭＋양끝 벽 여유를 수용해야 한다. 공간을 나눈 뒤 임의로 문을 붙이는 순서가 아니다.
7. **이동 공간:** 층별 외곽 B, 장애물 O_j, 수평 이동 여유 원판 D(r+m)에 대해 `F = (B ⊖ D) − ∪(O_j ⊕ D)`를 캐릭터 중심이 통과할 후보 영역으로 계산한다. 이는 수평 근사이며 계단의 경사·턱·머리 공간·상하 도착점은 별도로 계산한다. 문 유효폭의 필요조건은 `w≥2(r+m)`다. 실제 Controller/NavMesh 동작 성공을 이 식만으로 대체하지 않는다.
8. **수직·사생활:** 층간 코어·개구부·참은 같은 원본을 공유한다. 필수 방은 지정된 출입 상태에서 도달 가능해야 하고, 공용 이동이 개인 침실이나 다른 세대를 관통해서는 안 된다. 모든 방에 출구 2개를 강제하지 않는다. 대체 동선/잠긴 문은 해당 건물과 게임 계약이 요구할 때만 추가한다.
9. **확률의 범위:** 필수 기능/동선/설비는 확률로 빠지지 않는다. 적합한 유형 후보, 동등한 배치 후보, 선택 소품만 가중 추첨한다. `seed + stable Site/Building/Room ID + stage ID`로 난수 범위를 나누는 것이 후보이며, 한 방의 보정 때문에 다른 건물 전체가 바뀌지 않도록 한다.

하드 제약을 충족한 후보 사이에서 불필요한 복도 면적·목표 수용량 편차·과도한 길이를 줄일 수 있다. 그러나 점수 하나가 현실성/미술 품질의 증명은 아니다. **기하 적합성, 기능 충족, 실제 이동, 사용자의 공간/외형 판단은 서로 다른 판정**으로 남긴다. 실제 건축 법규 승인 모델도 아니다.

### A29-7 후속 작업그래프와 최소 실험

**다음 구현 때 실행기에 넣을 제안이며 이번에는 실행하지 않았다.** 제작 계산은 연속 실행하고 합격 관측은 마지막의 필요한 사례에 모은다. 알고리즘 중 해 없음/입력 불일치 검출은 계산의 일부다.

```text
요청/확정 조건 → 유형·수용량 프로그램 → 부지/접근 예약
 → 계단·참·공용/서비스 동선 → 세대/방/문 계산
 → 설비 수·점유/사용 공간 배치 → 구조·Collider·가림 파생
 → 최종 대표 이동/층 연결/수용량 확인 → 사용자 공간·외형 판단
```

| 실패 | 원인 소유 단계 | 필요한 재계산 범위 |
|---|---|---|
| 목표 설비가 들어가지 않음 | 프로그램/방 치수 또는 설비 배치 | 배치만 바꿔 되는지 먼저 판정. 불가능하면 해당 방/평면 또는 적합 필지 후보만. 가구/캐릭터 강제 축소 금지 |
| 계단 하부/상부에 접근 못 함 | 동선·코어 | 해당 코어/인접실, 종속 구조·NavMesh. 계단 Scene 오브젝트만 옮겨 덮지 않음 |
| 모텔 주차/수영장/객실 동을 함께 못 넣음 | 부지/유형 | 적합한 더 큰 부지나 허용된 다른 유형. 객실·욕실·서비스를 몰래 생략하지 않음 |
| 외관 창문과 실내 벽/층이 충돌 | 구조 파생 | 평면 경계와 층에서 창호를 다시 파생. 별도 외관 원본을 만들지 않음 |
| 충돌은 없지만 방이 텅 빔 | 목표 수용량/설비 계약 | 누락된 역할/개수 산정. 소품 무작위 살포를 해결로 쓰지 않음 |
| 공간은 맞는데 미술적 비례/가독성이 안 맞음 | 아트·카메라 평가 | 사용자 피드백으로 해당 표현 단계만 재개. 실제 방 크기와 카메라를 동시에 임의 변경하지 않음 |

최소 실험 후보는 세 가지다. 수치는 **검토용 입력이며 사용자 확정/구현값이 아니다**.

- **기존 카페 수용량:** 8석/16석 두 입력에서 필요한 모듈 수와 방 치수가 함께 변하고, 문/주 통로/주방/WC 접근을 유지하는지 확인한다. 현재 최대 4석 배치와 구분되는 실험이다.
- **모텔 부지:** 총 16객실을 2층에 배분하고 주차·수영장/데크·프런트·린넨 공간을 하나의 SitePlan으로 계산한다. 객실/주차/수영장 치수는 먼저 설계 입력으로 정해야 하며, 적합하지 않은 부지는 실패로 남긴다.
- **한국식 상가주택:** 1층 상가와 독립된 공용 계단, 위층 2세대, 각 세대의 거실/주방·침실·욕실이 서로 맞는 출입 관계를 갖는지 확인한다. 침실 경유 공용 이동과 상가 내부 경유 주거 출입을 반례로 둔다.

대표 사례가 사용자에게 쓸 만하다고 확인된 뒤 템플릿을 늘린다. 새로운 역할/코어/부지 제약이 없는 단순 변형마다 전 도시 생성과 이동 시험을 반복하지 않는다. 다음 구현도 기존 Player·카메라·0.2m 단차·층별 가림 계약을 보존해야 하며, 별도 제작 프로그램이 기존 게임 소유권을 대체하지 않는다.

기존 OBB 건물의 `폭 {12,14,16,18}m × 깊이 {10,12,14}m`를 입력으로 쓰며 모두 최소 12×10m부터 계산한다. 기존 대표 마트·경찰·주거의 선택 순서와 14×12m 하한은 유지하고 카페·소매점을 추가 선택한다. 이후 기존 `Retail` 건물에도 footprint와 BuildingIndex로 결정한 상가 유형을 적용한다. 의료 POI는 제외한다. 새 seed 난수나 강제 scale로 크기 차이를 만드는 방식이 아니다. 이 단계의 크기/방 수는 게임 프로토타입 가정이며, 모든 도시나 실제 건축에 적합한 범용 평면도라는 주장이 아니다.

WC·싱크·카운터·카페 테이블/의자는 역할과 물리 치수를 가진 단순 기하 설비이며 기존 재료를 사용한다. 기존 shelf/desk는 원래 크기로 재사용한다. **이 설비가 완성된 픽셀 가구나 사용자 승인 아트라는 뜻은 아니다.** 새 픽셀화·조명·투영 파이프라인은 도입하지 않는다.

## A28 계산·검사 계약

원본은 계속 `UrbanFloorPlan`이다. `UrbanCommercialFloorPlans`는 기존 건물 로컬 XZ 미터에서 프로그램별 방 Rect와 partition을 계산한다. `L/R=±W/2∓0.2`, `B/F=±D/2∓0.2`이며 +Z가 정문이다. 일반실 최소 치수2.4m, 서비스 복도1.8m, 실내 문1.6m, 후면 납품문1.8m는 현재 캐릭터 이동을 위한 프로토타입 모듈이다.

- 식료품점: 후방3.2m 지원실 띠 + 앞쪽1.8m 복도 + 나머지 판매장. 직원실/WC 폭은 각각2.8m이고 남는 후방 폭이 창고다.
- 카페: 후방3.2m 지원실 띠 +1.8m 복도. 창고/직원실/WC는 폭2.4m씩, 남는 폭은 주방이다. 전면은 우측3m 서비스 영역과 나머지 접객 영역으로 분리한다.
- 소매점: 후방5.2m 구간에 왼쪽 재고실, 폭1.8m 종방향 통로, 오른쪽 폭3.2m의 직원실/WC를 둔다. 오른쪽 두 실 깊이는 각각2.6m이고 남는 전면이 판매장이다.
- 입구 방은 문자열 이름이 아니라 `EntryPoint=(0,D/2−0.5)`를 포함하는 0층 방으로 찾는다. 후면문은 외벽 `z=−D/2`에서 창고/주방에 직접 연결되며 동일 opening이 메시와 Collider의 원본이다.
- 방 그래프 BFS는 입구부터 모든 방 연결을 검사한다. WC는 주방·창고·직원실을 통과 금지한 별도 BFS에서도 도달해야 한다. 기하 연결 통과는 실제 NavMesh/이동 성공을 대신하지 않는다.
- 가구는 방 안 점유 영역·벽·다른 설비·문 접근 여유를 계산한다. 적합하지 않은 가구를 축소하지 않으며 계획/설비 오류에 귀속한다. 실제 출입구 밖 접근도 마지막 이동 관측에 포함한다.

작업그래프는 `LocalOnly/WorkLoop/urban-commercial28/graph.json`, 상태는 `state.json`, 상세 계약은 `design.md`다. 흐름은 `implementation → observe → check → review`이며 구현 내부의 `필지 선택 → 프로그램 분할 → 문/구조 → 설비 배치`는 각각 계산과 오류 책임을 갖는다. 구현 후 읽기 입력인 design.md에 결과를 기록하여 원 그래프 의존성이 무효화됐고 `no_matching_edge`로 정지했다. 이를 성공으로 바꾸거나 구현/Play를 다시 실행하지 않았다. 같은 `check.py`와 실제 증거만 소비하는 `validation-graph.json`/`validation-state.json`으로 인계해 exit_code=0, errors=[]를 확인했다. 현재 review ticket은 `0eb7337347ac442eaf669f0a4b9787bc`이며 실제 사용자 답변 대기다. 다음부터 고정 설계 입력과 결과 기록을 분리한다. 파일 생성이나 AI 자체 외형 평가는 합격 증거가 아니다.

## A27 승인된 기준과 이력

상태: **v2 구조 구현·대표 Play Mode 호출 확인, 사용자 구조 유지 확정**. 사용자는 “구조 유지, 세부 설비·디자인은 다음 작업”으로 답했다. 현재 계단 위치와 방·복도 배치를 프로토타입 기준으로 유지하며, 완성 외형 승인이나 추가 설비 구현 권한으로 확대하지 않는다. 기존 [도심 인수인계](urban_pipeline_handoff.md)의 단일 실내와 외관뿐인 2층을 실제 방·층 연결로 확장한 결과다. 이 문서의 시험 치수는 최종 디자인 확정값이나 건축 법규 충족 주장이 아니다.

사용자 요구 원문:

> 도심 건축 알고리즘이 많이빡센가? 어떻게해야하지. 판타지 컨셉아트나 현대판타지 도심의 컨셉아트를 먼저만든뒤 그 건물을 하나하나 한50개는 설계해야할텐데 . 생성방식도설계해야하고 생성방식의모듈화 등등 기술적으로먼저 검토하고 설계해야하는데 너가 정리한뒤만들어봐 지금하다만 도심부터. 건물도 그냥 내부만 뻥뚫어놓고 어떤 설계도도없잖아. 2층도없고. 내부도좁고. 주차장이나 마트 경찰서 등등도없고. 방구분없고. 이런것들 찾아서 정리한뒤 프로토타입만 만들어봐

- 결과: 기존 도심의 서로 가까운 대표 필지 네 곳에 마트·2층 경찰서·2층 주거·주차장을 배치하고 실제 입구, 방 분리, 상층 이동을 제공한다.
- 메커니즘: 기존 도로/OBB 필지 → 용도별 공간 프로그램 → 치수 있는 평면도 → 벽/문/층판/계단 → 방 역할별 소품 → 기존 물리/NavMesh/가림 → 실제 Player 관찰.
- 보존: 기존 도로 생성, 0.2m 단차, 카메라, 같은 런타임 Player의 이동/씬 흐름, 기존 픽셀 재료 및 자산. 전체 도시 아트 재생성이나 렌더러 교체를 하지 않는다.
- 제외: 완성 아트 50개 저작, 새로운 전리품/위험/보상 정책, 임의 새 에셋 도입. 기존 3D 외형을 픽셀 완성품으로 승인하는 작업도 아니다.
- 판정: 대표 건물 입구·방·계단 왕복의 Play Mode 호출, NavMesh 연결, 소품 여유 공간, 현재 카메라에서 실제 화면. 물리 키 입력 확인과 구분한다.

대표 건물 필지는 최소 14×12m이며 적합 필지가 없으면 실패로 남긴다. 경찰서는 기존 `Office` 용도의 명시적 건축 프로그램 하위형으로 선택하여 루팅 등 기존 enum/정책을 보존한다. 주차장은 미사용 필지를 예약하고 건물 생성을 생략하는 별도 지면 프로그램이다. 카메라 보존 비교는 기존 `IsometricUrbanView`의 정상 도심 진입 설정이 끝난 뒤를 기준으로 하며, 기지→도심의 기존 자동 설정 차이는 허용한다. 별도 콘셉트 이미지는 아직 생성하지 않는다.

| 필지 → CGA 외관 분할 → 임의 실내 | 층·창문·외벽 반복을 간단히 변형 | 외형과 내부가 분리되어 계단/문/방을 보장하지 않음 | 외관 모듈화의 근거로만 사용 |
| POI 방 그래프 → 확률 모델/최적화 → 평면도 | 공간 용도와 인접성, 다층 관계를 표현 | 데이터 학습·탐색 비용, 기하학적으로 불가능한 요구 | 공간 프로그램 개념 채택. 범용 학습/최적화기는 도입하지 않음 |
| POI 방 그래프 → 직교 분할 템플릿 → 치수 제약 → 실제 구조 | 결정적이고 작으며 실패 부위를 특정 가능 | 면적/문 길이/계단 코어가 부족한 필지 | **이번 채택**. 최소 치수 미달은 후보 거절, 강제 축소 금지 |
| WFC → 방/도시 전체 | 국소 모듈의 인접 패턴에 강함 | 모순, 전역 도달성·필수 POI·계단 연결은 별도 제약 필요 | 주 구조에는 보류. 장식/타일 변형의 후속 후보 |

근거는 알고리즘의 역할을 설명하며, 현재 Unity 통합 성공을 대신하지 않는다. 외부 논문의 학습 데이터·코드·상용 도구를 설치한 것은 아니다.

1. [Parish & Müller, Procedural Modeling of Cities](https://people.eecs.berkeley.edu/~sequin/CS285/PAPERS/Parish_Muller01.pdf): 도로의 전역 목표·지역 제약과 필지/건물 단계 분리. 현재의 road graph·OBB 필지 구조를 유지하는 근거다.
2. [Merrell·Schkufza·Koltun, Computer-Generated Residential Building Layouts](https://www.cs.princeton.edu/courses/archive/spring11/cos598A/pdfs/Merrell10a.pdf): 방 목록·크기·인접 관계의 architectural program을 먼저 만들고 다층 평면도로 구체화한다. 주거 연구이므로 마트/경찰 용도는 프로젝트 프로그램으로 별도 저작한다.
3. [Esri CityEngine 기본 shape grammar](https://doc.arcgis.com/en/cityengine/2024.0/tutorials/tutorial-6-basic-shape-grammar.htm): 건물 면 → 층 → 벽/창문 타일의 반복 분할. 외관 문법만으로 내부를 얻을 수 있다고 해석하지 않는다.
4. [WFC 원저자 저장소](https://github.com/mxgmn/WaveFunctionCollapse): 국소 인접 패턴과 모순 처리의 범위. 필수 POI와 전역 연결성은 별도 계약이어야 한다.
5. [Unity CharacterController](https://docs.unity3d.com/6000.0/Documentation/Manual/class-CharacterController.html): stepOffset·slopeLimit·Move 기반 충돌 이동. 식만 맞는 계단을 실제 이동 성공으로 간주하지 않는다.
6. [Unity NavMeshSurface](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavMeshSurface.html): 수집 geometry와 agent/voxel 설정이 통로·층 연결 결과에 영향을 준다. 설치된 패키지의 실제 API/설정과 대조한다.

## 원본 표현과 생성 순서

```text
seed + 기존 RoadGraph/OBB 필지 + BuildingProgram
 → 후보 필지/정면 선택
 → StairCore·입구·복도 예약
 → FloorPlan(RoomRect, Opening, FloorIndex, Stair, PropSocket)
 → 공통 경계에서 벽/문 생성 + 계단 구멍을 제외한 층판
 → 별도의 시각 계단/이동 Collider
 → 방 역할별 기존 소품 배치
 → 기존 층별 가림/물리/NavMesh
 → 실제 플레이 관찰 + 사용자 피드백
```

원본은 평면도 데이터다. Mesh/Collider/NavMesh/가림 목록은 파생 결과다. 이름·색상만 다른 빈 건물을 프로그램이 다르다고 세지 않는다. 사후 Scene 오브젝트 이동을 평면도 변경 대신 사용하지 않는다.

| 데이터 | 권위·내용 | 소비자 |
|---|---|---|
| 기존 도시 Layout | seed, 도로, 블록, OBB 중심/크기/정면 | 대표 필지 선택 |
| BuildingProgram | 용도, 필요한 방/인접 관계, 층수, 최소 치수 | 평면도 계산 |
| FloorPlan | 건물 로컬 미터의 방, 벽 경계, 문 구간, 계단 코어, 층 높이 | 구조/충돌/소품/가림 |
| Room/Opening graph | RoomId, 역할, FloorIndex, 연결 양 끝 | 통로 검사, 소품 역할, 미리보기 표식 |
| PropSocket | RoomId, local pose, 점유/사용 여유 공간 | 기존 소품 catalog·배치 |

각 계산은 다음과 같이 귀속한다. `SelectParcel`은 필지 적합성, `PlanRooms`는 방/문/층 관계, `RealizeStructure`는 실제 기하·Collider, `PlaceProps`는 역할/여유 공간을 소유한다. 검사는 마지막 필요한 범위에 모으며 `ROOM_OVERLAP`, `MISSING_DOOR`, `STAIR_HEADROOM`, `NAV_DISCONNECTED`, `PROP_CLEARANCE` 같은 실패를 해당 단계로 돌린다. 전체 도시 재생성은 기본 복구가 아니다.

## 좌표·변환·치수 계약

`입력 필지 → 건물 canonical XZ/FloorIndex → Unity local mesh/Collider → Unity world → 기존 view/clip/screen → 기존 렌더 출력`

| 공간 | 원점/축/단위/상위 |
|---|---|
| 필지 | 기존 Layout의 world XZ 중심, meter, 정면 벡터와 OBB 기저 유지 |
| 건물 canonical | footprint 중심의 1층 기준 높이, +X 오른쪽/+Y 위/+Z 정면, Unity 좌수계, meter, scale=1 |
| 층 | canonical의 XZ와 동일, 높이 `h_f = f·3.4m`, zero-based FloorIndex, 상위=건물 |
| Mesh/Collider | 같은 canonical plan에서 생성, scale 중복 적용 없음. box의 치수 표현용 localScale은 원본 길이이며 전체 건물 왜곡과 구분 |
| world | `p_w = c + Quaternion.Euler(0,yaw,0) * p_local`, degree, yaw 한 번 적용, 상위=기존 도시 root |
| view/clip/screen | 현재 게임 카메라/API 규약 유지. 관찰을 위해 카메라 각도/줌/투영을 바꾸지 않음 |

연속 XZ/yaw는 유지하고 픽셀 표현 때문에 실제 물리 좌표를 snap하지 않는다. 새 UV/픽셀 알고리즘을 추가하지 않으며 기존 atlas/정면 계약을 사용한다. 투영/가림에는 정보 손실이 있으므로 스크린샷 하나를 3D 구조의 전체 증거로 간주하지 않는다.

프로토타입 치수: 복도 2.4m, 문 유효 폭 1.6m, 계단 폭 2.2m, 층고 3.4m, 계단 수평 진행 길이 최소 6m, 뒤 참 1.6m·앞 참 2.4m. 필지에 이를 충족하는 여유가 없으면 다른 필지를 선택한다. 기존 폭·깊이를 억지로 축소하지 않는다.

- 경사 높이 `h(s)=H·clamp(s/L,0,1)`, 경사각 `atan(H/L)`. `H=3.4,L=6`일 때 약 29.54도이며 실제 CharacterController·NavMesh slope 한도 이하이어야 한다.
- 시각 계단의 각 단 높이 `H/n`, 진행 폭 `L/n`; 이동 Collider는 동일 끝점의 연속 경사면이다. 단수 선택이 층 도착 높이를 바꾸지 않는다.
- 상층 층판에서 같은 stair core footprint를 빼고 남은 직사각 영역만 생성한다. 덮은 층판 위에 계단을 삽입하지 않는다.
- 공통 벽은 중복 생성하지 않으며, 문 구간을 제외한 벽과 문 위 lintel은 같은 경계 데이터에서 나온다.
- 방 그래프의 연결은 문 구간이 양쪽 실제 공간에 접할 때만 유효하다. 벽 너머 두 방 중심이 가깝다는 이유로 연결하지 않는다.
- 상층/지붕/벽의 시각 가림은 기존 fader에 층 정보를 더해 처리한다. 렌더 숨김과 Collider 제거를 혼동하지 않는다.

### A27-v2 계단·층 경계 교정 계약

최신 사용자 정정:

> 계단이 접근불가능한곳에 되어있는둥 이상한데 설계도를 차라리 다른데서참고하던지

v1에서 계단의 낮은 시작점이 건물 뒤에 있었고 높은 끝이 앞 로비에 닿았다. 경사 자체의 왕복 가능성과 현관에서 읽히는 접근 동선은 다른 조건이다. **앞 로비 2.4m를 순환 동선의 기준으로 두고 낮은 시작점을 앞 로비에 직접 연결하며, 상층 뒤 참을 중앙복도로 연결하는 직선계단**으로 수정한다.

- 로컬 `Rect.y`는 Unity의 높이가 아니라 canonical Z다. `Start=(Bounds.center.x, Bounds.yMax)`가 앞쪽 낮은 점, `End=(Bounds.center.x, Bounds.yMin)`이 뒤쪽 높은 점이다. `d=normalize(End-Start)`, 아래 참 관측점은 `Start-d·0.65m`, 위 참 관측점은 `End+d·0.65m`로 같은 방향식에서 계산한다. 기존 ±Z 상수로 다시 뒤집지 않는다.
- 도로 밖/현관 → 앞 로비 → 계단 하단 → 상층 뒤 참 → 중앙복도 → 각 방 → 귀환을 실제 이동 경로로 관측한다. 계단 하단에 순간이동한 뒤 왕복만 성공시킨 것은 이 계약의 증거가 아니다.
- 층판 두께 0.2m를 반영하여 하층 벽의 높이를 `floorHeight-0.2m`로 생성하는 수정안을 시험한다. **가설:** 하층 벽 윗면과 상층 보행면의 coplanar NotWalkable 경계가 상층 문을 막을 수 있다. 실제 Collider/NavMesh 관측과 수정 후 경로로 판정하며 현재 원인 확정은 아니다. NavMesh 샘플 허용 반경 확대로 다른 층/벽을 찍어 덮지 않는다.
- 가구가 있을 수 있는 방 중심을 무조건 도착점으로 삼지 않는다. `HasDoor` 방의 WalkAnchor는 문 중심에서 방 중심 방향으로 0.9m 안쪽, 공용 공간은 그 공간 중심을 사용한다. 이 앵커의 보행 가능성과 소품 여유를 함께 확인하며 실패하면 앵커/배치 계약에 귀속한다.

직선계단 동선의 근거는 [San Francisco Planning Department — Trocadero Clubhouse](https://commissions.sfplanning.org/hpcpackets/2021-003608DES.pdf)의 PDF 23쪽(0-based 22), 본문 7쪽 `Interior Description`이다. 직사각형에 가까운 2층 건물의 주출입→전실→계단 홀→직선계단, 상층 계단 끝→복도→개별 방 연결이 명시된다. 이 **동선 유형**을 참고하며 평면도·장식·치수를 복제하지 않는다. 원문도 상층 설명은 도면 근거이고 현장 직접 관찰은 아니라고 구분한다.

비교 자료는 원설계사의 [Mascord 21109](https://houseplans.co/house-plans/21109/)로, 현관→foyer→U자계단을 설명한다. 입구와 계단을 함께 계획하는 근거지만 이번 직선계단의 모양 출처는 아니다. [Avon Project Services의 Burley 주택 도면](https://www.newforestnpa.gov.uk/wp-content/uploads/2026/03/P574-201-Rev-A-Proposed.pdf)에는 entrance hall·상층 landing 및 별도 계단 머리 공간 명세가 있다. 공개 도면의 저작물은 프로젝트 자산으로 복제하지 않는다. 웹 PDF screenshot은 cache miss로 실패하여 도면 이미지를 직접 시각 확인했다고 기록하지 않는다.

마트/경찰/주거의 세부 방 이름·개수는 실제 구현 평면도에 기록한다. 위 프로그램은 구조 프로토타입이며 현실 시설의 법적·운영상 완전한 설계라는 뜻이 아니다.

## 50개로 확장하는 카탈로그 설계

**10개 공간 프로그램 × 5개 평면도 변형 슬롯 = 50개 설계 ID 구조**를 제안한다. 지금 50개 자산이나 50개 평면도가 완성됐다는 의미가 아니다. 외벽 색만 바꾼 결과를 독립 설계로 세지 않는다.

| 프로그램 계열 | 프로그램에 남길 구역 |
|---|---|
| 식료품 마트 | 판매·계산·창고·직원·하역 |
| 경찰 | 민원·사무·조사·보관·휴게 |
| 단독 주거 | 공용·주방·침실·욕실·보관 |
| 상가주택 | 판매/업무층·별도 주거층·계단 |
| 공동주거 | 공용 접근·반복 세대·설비 |
| 진료/약국 | 접수·대기·진료/조제·보관 |
| 음식점 | 홀·조리·보관·직원 |
| 작업장 | 작업·자재·사무·하역 |
| 사무/행정 | 접수·업무·회의·보관 |
| 주차/서비스 | 진입·통로·주차·보행 |

다섯 슬롯은 소형 전면 진입, 넓은 전면 진입, 코너/측면 진입, 서비스 접근 분리, 복합/증축형 같은 **실제로 다른 공간 조건**으로 관리한다. 모든 프로그램에 같은 변형을 무조건 강제하지 않는다. 각 슬롯에 `programId, variantId, minFootprint, floors, requiredRooms, adjacency, stairCore, doorRules, propRules, artStyleId`를 저장하고 실현 불가능하면 미저작/부적합으로 남긴다.

콘셉트아트는 팔레트·재료·창문/지붕 리듬·현대판타지 장식의 참고로 연결하고 방/출입/층의 원본을 대신하지 않는다. 기존 GDD §14.1 픽셀 목표가 유지된다. 구조가 통과한 뒤 선택한 대표 프로그램의 외관/실내 콘셉트를 사용자와 확인하고 필요한 자산만 추가한다.

## A27 최소 실험·자동 검사 명세

가설: 현재 OBB 지역 좌표와 입구/물리 경로를 유지하면서 프로그램별 평면도와 계단 코어를 추가하면, 빈 실내를 실제 기능 공간으로 나누고 같은 Player가 상층까지 이동할 수 있다. 맞으면 네 프로그램이 실제 생성되고 방·층으로 이동한다. 틀리면 실패 필드의 담당 계산을 수정하며 카메라/전체 도시/아트를 바꿔 덮지 않는다.

## 실행기와 결과 인계

현재 그래프: `LocalOnly/WorkLoop/urban-architecture27/graph-v2.json`, 상태 `state-v2.json`. v1의 `graph.json`·`state.json`은 보존하고 state는 stop한다. `implementation → observe → check → review` 네 작업 단위로 제한한다. 구현 단위 안에서 `SelectParcel → PlanRooms →RealizeStructure → PlaceProps`를 각각 결정적 계산과 실패 책임으로 구현하고, 전 과정을 큰 ai.work 설명과 파일 검사로 대체하지 않는다.

`observe`는 Unity 실제 관측을 `readback.json`과 각 프로그램의 실제 PNG 네 장에 저장한다(설명용 평면도는 선택 추가). `check`의 고정 Python 알고리즘은 필수 필드·프로그램별 방/층·이동/NavMesh·보존·미리보기 파일을 판정한다. 실제 관측이 틀렸다면 이 판정도 틀릴 수 있으므로 원본 도구 출력과 Unity 측정 경로를 함께 보존한다. hash는 의미적 정확성의 증명이 아니다.

### v1 실제 관측과 실패

`LocalOnly/WorkLoop/urban-architecture27/readback-v1.json`에 실제 Unity 관측을 보존했다(SHA-256 `9a4a8004cb4cc8aa6da159358cda3910ab31547f539c31cc04eda3d2af747dcd`). 기존 `readback.json`과 동일 바이트의 복사본이며 v2 결과로 덮어쓰지 않는다.

| 관측 | v1 실제 결과 | 판정 |
|---|---|---|
| 마트 | 3개 방 도달, 이동오류 0 | 제한된 Play Mode 호출 확인 |
| 경찰/주거 계단 | 각각 upReached/downReached/navMeshConnected=true | 경사 왕복 확인. 계단 배치의 사용자 승인 아님 |
| 경찰 상층 | Detective office 경로 `PathPartial`, 전체 12공간 중9 도달 | 미완료. 하층 벽 coplanar 경계/가구와 목표점 겹침은 조사 가설이며 원인 미확정 |
| 주거 상층 | Bedroom 중심 NavMesh sample 실패, 전체12공간 중9 도달 | 미완료. 가구와 겹칠 수 있는 방 중심을 무조건 도착점으로 삼은 앵커 계약 수정 대상 |
| 전체 예외/보존 | compileErrors=0, top-level errors=[], 보존4필드true | 개별 방 이동실패를 상쇄하지 않음 |

v1 판정기는 `movementErrors`와 `roomsReached`를 소비하지 않는 누락이 있었다. 따라서 이 판정기로 기술 합격을 선언할 수 없으며, 실제 v1 기술 통과/미술 승인은 제출하지 않았다. v2는 프로그램별 `roomsReached==roomCount`, `movementErrors==[]`, 계단별 `errors==[]`, 최상위 `errors==[]`를 필수로 소비한다. 주차장을 제외한 세 건물에는 `occlusionErrors==[]`도 필요하다. 사용자 정정과 실제 실패로부터 계약을 강화한 새 버전이며 같은 실패 관측을 성공으로 재분류하지 않는다.

가림의 실제 관측은 지상층 실내에서 상층 renderer/roof 숨김 및 현재층 renderer 유지, 상층 실내에서 상층 renderer 표시/roof 숨김, 실외에서 renderer 복원, 전 과정 Collider 유지로 구분한다. `occlusionErrors`의 누락이나 아직 측정하지 않은 빈 배열은 통과 증거가 아니다. Unity 관측 담당자가 이 상태를 실제로 읽은 뒤에만 실패 목록을 확정한다.
